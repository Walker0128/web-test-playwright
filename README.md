# Webテスト課題 - Sauce Demo

## 概要

このリポジトリは、公開デモサイトである Sauce Demo を対象にした手動テストケースおよびUI自動テストをまとめたものです。

- 対象サイト: https://www.saucedemo.com/
- 自動化ツール: Playwright / TypeScript
- CI: GitHub Actions
- 設計方針: Page Object Model

## 対象サイト選定理由

Sauce Demo は、ログイン、商品一覧、商品詳細、カート、チェックアウトなど、ECサイトに近い基本的なユーザーフローを安全に確認できる公開デモサイトです。

当初は実際のSaaSプロダクトを対象にすることも検討しましたが、実アカウントを利用した自動テストをPublicリポジトリやCI上で実行することは、アカウント情報・テストデータ・本番環境操作に関するリスクを伴う可能性があります。

そのため、本課題では安全に再現可能なデモサイトを対象とし、テスト設計、自動化実装、CI実行、保守性を重視した構成にしています。

### 非機能 / セキュリティ観点

#### パフォーマンス

- [ ] ログイン画面が一定時間内に表示されること
- [ ] ログイン後の商品一覧画面が一定時間内に表示されること
- [ ] 商品詳細画面・カート画面・チェックアウト画面への遷移が極端に遅くならないこと
- [ ] 商品画像や主要UIコンポーネントが正しく読み込まれること
- [ ] ページリフレッシュ後も、表示完了までの時間が許容範囲内であること
- [ ] 操作後の画面反応が遅すぎず、ユーザー体験を損なわないこと
- [ ] 主要操作中に不要なリクエストが大量発生していないこと
- [ ] APIや静的リソースの 4xx / 5xx エラーが発生していないこと

#### ストレステスト / 負荷テスト

- [ ] 複数ユーザーが同時にログイン・商品閲覧・カート操作を行っても、サービスが安定して動作すること
- [ ] 短時間に多数のリクエストが発生した場合でも、システムがクラッシュしないこと
- [ ] 高負荷時にレスポンスが遅くなった場合でも、ユーザーに分かりやすい状態表示またはエラー表示が行われること
- [ ] 高負荷時に注文処理・カート状態・在庫状態などのデータ不整合が発生しないこと
- [ ] 同一操作を連続実行しても、二重注文・二重追加・重複処理が発生しないこと
- [ ] レート制限やアクセス制御がある場合、制限超過時に適切なレスポンスが返されること
- [ ] 高負荷時のログ・メトリクス・エラー内容を確認できること

#### APIリクエスト改ざん・不正利用対策

- [ ] APIリクエストのパラメータを改ざんしても、想定外の商品追加・削除・注文処理が実行されないこと
- [ ] フロントエンド上の操作を経由せずに不正なリクエストを送信しても、権限チェック・入力チェックが正しく行われること
- [ ] 他ユーザーのカート情報・注文情報にアクセスできないこと
- [ ] セッション情報や認証トークンが無効・期限切れの場合、API操作が拒否されること
- [ ] APIエラー発生時に、内部情報・スタックトレース・機密情報がレスポンスに含まれないこと
- [ ] 価格・数量・商品IDなどの重要データを改ざんしても、サーバー側で正しく検証されること
- [ ] 連続したAPI操作や重複リクエストにより、二重注文・二重決済・不整合なカート状態が発生しないこと

#### スクレイピング / Botアクセス対策

- [ ] 短時間に大量アクセスが発生した場合、サービスが不安定にならないこと
- [ ] Pythonなどの自動化ツールによる連続アクセスに対して、必要に応じて制限・検知・ブロックが行われること
- [ ] 商品一覧・商品詳細などの公開情報が、想定外の頻度で大量取得されないこと
- [ ] Botアクセスによって、通常ユーザーの画面表示・操作に影響が出ないこと
- [ ] 不自然なアクセスパターンがログ・監視で検知できること
- [ ] User-Agentやアクセス頻度などに基づき、不正または過剰なアクセスを調査できること
- [ ] レート制限がある場合、制限超過時に適切なエラーレスポンスが返されること

## プロジェクト構成

```text
.github/
└── workflows/
    └── playwright.yml

 tests/
├── data/
│   └── saucedemo.data.ts
├── pages/
│   ├── base.page.ts
│   ├── cart.page.ts
│   ├── checkout-complete.page.ts
│   ├── checkout-information.page.ts
│   ├── checkout-overview.page.ts
│   ├── inventory.page.ts
│   ├── item-detail.page.ts
│   └── login.page.ts
└── saucedemo.spec.ts
```

自動テストは Page Object Model を採用し、テストシナリオ、画面操作・検証、テストデータを分離しています。

- `tests/saucedemo.spec.ts`: テストシナリオとテストステップ
- `tests/pages/`: 各画面ごとの操作・表示確認・検証処理
- `tests/data/`: ユーザー、商品、チェックアウト情報、メッセージなどのテストデータ

この構成により、現在は2件の代表ケースのみを実装していますが、実務でケース数が増えた場合も、画面単位で保守・拡張しやすくなっています。

## ローカル実行方法

依存関係をインストールします。

```bash
npm install
```

Playwrightのブラウザをインストールします。

```bash
npx playwright install --with-deps chromium
```

テストを実行します。

```bash
npm test
```

HTMLレポートを開きます。

```bash
npm run report
```

## CI Pipeline

GitHub Actions により、以下のタイミングでPlaywrightテストが自動実行されます。

- `main` ブランチへのpush
- `main` ブランチへのpull request
- 手動実行（workflow dispatch）

CIでは以下を実行します。

1. リポジトリをcheckoutする
2. Node.js 24をセットアップする
3. `npm ci` で依存関係をインストールする
4. Playwright Chromiumブラウザをインストールする
5. Playwrightテストを実行する
6. Playwright HTMLレポートをartifactとして保存する

Workflowファイルは以下に配置しています。

```text
.github/workflows/playwright.yml
```

## レポート・デバッグ方針

PlaywrightのHTMLレポートでテスト結果を確認できます。
また、検証しやすくするため、必要に応じて以下のartifactを利用します。

- screenshot
- video
- trace

`test.step()` を利用することで、レポート上でも各テストステップを確認しやすくしています。

## 補足

本リポジトリでは、Publicリポジトリとして公開しても問題がないように、実アカウント、シークレット、個人情報、内部API、実サービスの認証情報は扱っていません。

また、負荷テスト、ストレステスト、API改ざん、スクレイピング、Botアクセス確認などのセキュリティ・非機能テストは重要な観点として整理していますが、明確な許可がない外部公開サイトに対しては実行しない方針です。
